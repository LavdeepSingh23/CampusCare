# Database Journal

## Week 1 – Understanding the Requirements and Studying the Entities
This week I mainly focused on understanding the CampusCare project properly before starting the actual database work. I went through the different features of the system and tried to understand what kind of information would be needed at each stage. After looking at the student, doctor, receptionist and admin workflows, I started studying the possible entities that would be required in the database. I looked at things like students, doctors, specialties, RFID cards, visits, queues, consultations, prescriptions, dispensing and audit records. The main goal this week was not to finalize anything but to understand what data the system would need and how each part of the application would use it.

## Week 2 – Deciding the Main Entities and Drawing the DFD Level 1
After getting a better understanding of the requirements, I started deciding which entities should actually be included in the database. I went through the entities one by one and checked whether they were really needed for the project or whether some information could be kept as part of another entity. I also considered the fact that CampusCare needs to keep medical and visit history, so I tried to structure the entities in a way that would not cause old information to be lost whenever something is updated.

Alongside this, I worked on the **DFD Level 1** for CampusCare to get a clearer picture of how data actually flows between the different processes and users. This helped me see how a student, doctor, receptionist and admin interact with the system's main processes (like registration, queue management, consultation and prescription handling) and how data moves between these processes and the database. Drawing the DFD Level 1 made it easier to double-check that the entities I was planning could actually support all the data flows in the system. By the end of this week, I had a clearer list of the main entities that would form the base of the CampusCare database, backed by the DFD.

## Week 3 – Working on Relationships, Use Case Diagram and Class Diagram
Once the entities were decided, I started working on how they would be connected to each other. I looked at which entities would have one-to-one, one-to-many or other types of relationships and started figuring out where primary keys and foreign keys would be needed. For example, I worked on how a student would be connected to their RFID card and visits, how a visit would connect with a doctor and queue entry, and how consultations and prescriptions would be connected to a particular visit.

To support this, I also made a **use case diagram** to clearly map out what actions each type of user (student, doctor, receptionist, admin) can perform in the system, which helped confirm that the relationships I was planning actually matched the real interactions users would have. Along with this, I created a **class diagram** to represent the entities as classes along with their attributes and relationships, which gave a more structural view of the database and made it easier to see how the entities connect before actually implementing them in MySQL. This helped me understand the database more as a complete structure rather than just a collection of separate tables.

## Week 4 – Finalizing the Database Structure
This week I focused on putting everything together and checking whether the database structure made sense for the actual workflows of CampusCare. I reviewed the entities and relationships again and worked on the required keys, constraints and other database rules. I also checked important cases such as keeping previous visits, handling changes in student medical information and making sure the same student cannot have conflicting active visits. After going through these cases, I refined the structure so that it would be practical to implement in MySQL and could later be connected properly with the FastAPI backend.
